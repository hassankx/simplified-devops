Follow one commit through a secure pipeline

Seven stages, each with the checks that belong there. Pick what goes wrong, press Play, and watch which gate catches it.

Scenario

What fails the build

Adding scanners is the easy part. The decision that matters is what each finding does. This is an example policy; tune the thresholds to your own risk.

FindingActionWhy
Any secretBlockThere is no safe severity for a leaked credential. Rotate it.
Critical CVE, fix availableBlockThe remedy is an upgrade, so there is no reason to ship it.
CVE with no fixExceptionBlocking achieves nothing. Record an owner and an expiry date.
New vulnerability in changed codeBlockGate on new code so the author fixes it while it is fresh.
Old findings in untouched codeTicketFailing every build on legacy debt teaches people to ignore the gate.
High-severity IaC misconfigurationBlockA public bucket or open security group is cheapest to fix as a text file.
Unsigned imageRejectThe cluster refuses it at admission, whoever submitted it.
Runtime alertPage on-callIt already happened, so the only response left is fast detection.

Pipeline config

A GitHub Actions workflow with one job per stage, and the cluster policy that enforces signatures. It has not been run against a real repository: add your secrets, registry and paths, and pin each action to a version you have checked.

# .github/workflows/secure-pipeline.yml
name: secure-pipeline
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

env:
  IMAGE: ghcr.io/${{ github.repository }}

jobs:
  # CODE: static scans on every pull request
  code:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0            # full history, so old secrets are found too
      - name: Secrets scan (any finding fails)
        uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
      - name: SAST and quality gate
        uses: SonarSource/sonarqube-scan-action@v5
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          SONAR_HOST_URL: ${{ vars.SONAR_HOST_URL }}
        with:
          args: -Dsonar.qualitygate.wait=true   # fail the job if the gate fails
      - name: IaC scan
        uses: bridgecrewio/checkov-action@v12
        with:
          directory: infra/
          soft_fail: false
      - name: Dependency scan (blocks on fixable critical or high)
        uses: aquasecurity/trivy-action@0.28.0
        with:
          scan-type: fs
          scan-ref: .
          severity: CRITICAL,HIGH
          ignore-unfixed: true
          exit-code: "1"

  # BUILD: build the image, scan it, write the SBOM (main only)
  build:
    needs: code
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    outputs:
      digest: ${{ steps.build.outputs.digest }}
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - id: build
        uses: docker/build-push-action@v6
        with:
          push: true
          tags: ${{ env.IMAGE }}:${{ github.sha }}
      - name: Image scan (blocks on critical)
        uses: aquasecurity/trivy-action@0.28.0
        with:
          image-ref: ${{ env.IMAGE }}@${{ steps.build.outputs.digest }}
          severity: CRITICAL
          ignore-unfixed: true
          exit-code: "1"
      - name: SBOM
        uses: anchore/sbom-action@v0
        with:
          image: ${{ env.IMAGE }}@${{ steps.build.outputs.digest }}
          format: spdx-json
          output-file: sbom.spdx.json
          upload-artifact: false
      - uses: actions/upload-artifact@v4
        with:
          name: sbom
          path: sbom.spdx.json

  # TEST: attack the running app in staging
  test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      # assumes your staging deploy of this image happens before this step
      - name: DAST baseline
        uses: zaproxy/action-baseline@v0.14.0
        with:
          target: ${{ vars.STAGING_URL }}
          fail_action: true

  # RELEASE: sign the exact digest that passed, attach the SBOM
  release:
    needs: [build, test]
    runs-on: ubuntu-latest
    permissions:
      packages: write
      id-token: write               # keyless signing with the workflow identity
    steps:
      - uses: sigstore/cosign-installer@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: actions/download-artifact@v4
        with:
          name: sbom
      - name: Sign and attest
        env:
          REF: ${{ env.IMAGE }}@${{ needs.build.outputs.digest }}
        run: |
          cosign sign --yes "$REF"
          cosign attest --yes --type spdxjson --predicate sbom.spdx.json "$REF"

  # DEPLOY: by digest, behind a manual approval; the cluster verifies again
  deploy:
    needs: [build, release]
    runs-on: ubuntu-latest
    environment: production         # add required reviewers on this environment
    steps:
      # cluster credentials setup omitted
      - name: Roll out by digest
        run: |
          kubectl set image deployment/app \
            app="${IMAGE}@${{ needs.build.outputs.digest }}"

# Kyverno: reject any pod whose image was not signed by the workflow above
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-signed-images
spec:
  validationFailureAction: Enforce    # use Audit in dev to see violations first
  webhookTimeoutSeconds: 30
  rules:
    - name: verify-signature
      match:
        any:
          - resources:
              kinds: [Pod]
      verifyImages:
        - imageReferences:
            - "ghcr.io/your-org/*"
          attestors:
            - entries:
                - keyless:
                    issuer: https://token.actions.githubusercontent.com
                    subject: https://github.com/your-org/your-repo/.github/workflows/secure-pipeline.yml@refs/heads/main
                    rekor:
                      url: https://rekor.sigstore.dev

Interview questions

Short answers you can say aloud. Each stage above has one more.

The pipeline is green. What does that prove?

Only that the gates you defined passed. If the pipeline has no security gates, green means it compiled and deployed. A good answer names the gates: no secrets, no fixable critical CVEs, quality gate passed, image signed, admitted by policy.

How do you add security scans without slowing developers down?

Run the scans in parallel and cache the vulnerability databases. Gate only on new code and on findings that are severe and fixable. Send everything else to a backlog. Give results in the pull request, where the author already is.

What is an SBOM for?

It is the list of every package inside an image. When a new vulnerability is announced, you search the SBOMs to learn which deployed images contain the affected package, in minutes, without rescanning everything. Log4Shell is the standard example.

Where is the image signature checked, and by what?

By an admission controller in the cluster, such as Kyverno or OPA Gatekeeper, at the moment a pod is created. Checking in the pipeline alone is not enough, because the risk is a deploy that never went through the pipeline.

Who decides what blocks a release?

Security and engineering agree the policy together and store it as code. Thresholds are explicit, exceptions have an owner and an expiry date, and changing a rule is a reviewed pull request.

Which single check would you never skip?

Secrets scanning. It is fast, has few false positives when tuned, and a leaked credential gives an attacker direct access without needing any vulnerability at all.

What changed from the original diagram

  • IaC scanning moved from Test to Code. Checkov reads Terraform as text. It is static analysis, not dynamic testing.
  • SBOM generation moved from Release to Build. It is produced from the image when it is built, then signed at release.
  • Secrets scanning is its own check, separate from SAST. SonarQube does not replace Gitleaks or TruffleHog. Either of those two works.
  • Dependency scanning and image scanning are two steps. One reads your lockfile, the other reads the built image including its base layers.
  • k6 is removed. It is a load-testing tool and does not test security.
